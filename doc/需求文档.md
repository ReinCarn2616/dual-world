## 1. 项目概述

### 1.1 一句话定位

一个 2D 解谜平台跳跃游戏。同一张地图存在**光**与**暗**两个世界，起点和终点完全相同，但路线完全不同。玩家可以在**任意时刻**（奔跑中、跳跃中、静止时）瞬间切换所处的世界。任何一个世界都无法单独通关，玩家必须找出两个世界之间的互补关系，利用切换的瞬间改变自己的运动状态，才能抵达终点。

### 1.2 核心设计法则（不可违背）

这份文档里所有的规则都从下面四条推导而来。如果后续任何设计决策与这四条冲突，以这四条为准。

> **法则 1 — 切换的瞬间才是机制本体。**
> 两个世界本身只是布景，真正的玩法发生在"按下切换键的那一帧"。判据：如果静止时切换和运动中切换效果完全一样，那它就只是两条路拼起来，机制不成立。因此**切换必须保留玩家的位置与速度矢量**（见 §2.2）。

> **法则 2 — 单世界内必须无解。**
> 每一关都必须能被证明"只在光世界走不通，只在暗世界也走不通"。这是整个游戏的立身之本，是逐关验收的硬指标（见 §12）。

> **法则 3 — 失败必须零代价。**
> 切换失败、掉进坑里、碰到熔岩，都只导致"回到本关起点"，没有命数、没有惩罚、没有动画延迟。解谜游戏的生命线是"让玩家敢想"，一旦失败有成本，玩家就会停止思考、开始乱试，游戏立刻退化成手残跑酷。

> **法则 4 — 先冻结运动参数，再设计关卡。**
> 所有关卡的几何尺寸都建立在"能跳多高、能跳多远"之上。参数一旦在关卡设计完成后才调整，全部关卡都要重做。因此 §4.2 的数值必须在 Day 1 结束前锁定，之后只允许微调，不允许改量级。

### 1.3 使用场景

- **课堂答辩演示**：评审老师需要在 30 秒内看懂玩法、2 分钟内体验到"啊哈"时刻。
- **同学自行游玩**：完整通关时长目标 8–15 分钟。
- **移动端**：本版本只要求"能正常显示、不崩"，键盘操作是主线（见 §14 Q3）。

### 1.4 明确的范围边界

| 项 | 本版本 | 理由 |
| --- | --- | --- |
| 关卡数量 | **8 关**（最低可接受 6 关） | 双世界关卡设计成本翻倍，宁缺毋滥 |
| 世界切换 | 随时、无限次、零冷却 | 机制核心，不能被限制 |
| 计时与成绩 | **只做记录，不影响玩法**：本关用时 + 累计总用时 + 切换次数 | 见 §8，必须遵守 §8.1 的边界 |
| 存档 | 已解锁关卡进度 + 每关最佳成绩 + 全流程最佳 + 键位设置 | `localStorage` 分键存储，零成本（见 §8.4、§4.5.5） |
| **画面** | **必须是图形画面**，屏幕上不允许出现任何 ASCII 字符 | ASCII 仅是关卡几何的数据格式，玩家不可见（见 §7.5） |
| **美术资源** | 程序化占位图兜底，手绘 PNG 与 ComfyUI 离线产出逐层覆盖 | 见 §7.6、§7.7；素材缺失时游戏必须仍可玩 |
| **键位** | 6 个动作全部可自定义、可持久化、提示文案联动 | 见 §4.5 |
| 后端 / 网络请求 | **完全没有** | GitHub Pages 是纯静态托管 |
| 大模型 API | **绝对不使用** | 前端密钥必然泄露（见 §13 R6） |

## 2. 核心机制：双世界模型

### 2.1 数据模型

一个关卡 = **两张同尺寸的瓦片网格** + **一个共享的起点** + **一个共享的终点**。

```
关卡 (Stage)
├─ 光世界网格  light[rows][cols]   ← 2D 字符网格
├─ 暗世界网格  dark[rows][cols]    ← 与 light 严格同宽同高
├─ 起点 (startX, startY)           ← 两个世界共用，坐标唯一
└─ 终点 (exitX, exitY)             ← 两个世界共用，坐标唯一
```

- 网格尺寸固定为 **20 列 × 12 行**，瓦片 **32 px**，逻辑画布 **640 × 384**（见 §7.5.1）。
- 玩家任何时刻只"处于"其中一个世界，由 `worldIndex`（0 = 光，1 = 暗）表示。
- **起点与终点在两个世界的坐标必须一致**——这是"相同起点、相同终点"这一前提的数据层保证。

### 2.2 世界切换规则（本版本最重要的规则）

**决策：采用"切换失败并给反馈"方案。**（在"卡住必死"与"温柔挤出"之间选择）

#### 判定算法

```
函数 trySwitch(player):
    目标世界 = 另一个世界(worldIndex)
    box = 玩家在目标世界中的碰撞盒（位置与尺寸完全不变）

    若 box 与目标世界中任意实心瓦片相交：
        # 切换失败
        播放失败反馈（屏幕闪红 + 低频音效 + 轻微屏幕震动）
        玩家留在原世界
        玩家的位置、速度、状态 完全不变   ← 关键：不产生任何副作用
        返回 false
    否则：
        # 切换成功
        worldIndex = 目标世界
        # 玩家的位置 (x, y) 与速度 (vx, vy) 原样保留，不做任何修改
        播放成功反馈（整屏调色板突变 + 高频音效 + 轻微径向缩放）
        返回 true
```

#### 规则细节（必须实现一致）

| 编号 | 规则 | 说明 |
| --- | --- | --- |
| S1 | 位置完全保留 | 切换是"原地换世界"，不位移 |
| S2 | **速度矢量完全保留** | `vx`、`vy` 原样带入目标世界。这是"跳跃抛物线在空中被接续"的物理基础 |
| S3 | 判定使用玩家的完整 AABB | 不是只判定脚底或中心点，否则会出现"半个身子卡在墙里" |
| S4 | 单向平台（若实现）不参与失败判定 | 否则玩家在单向平台中会被无故拒绝 |
| S5 | 失败无代价 | 不扣血、不扣命、无冷却；只播放反馈 |
| S6 | 成功切换后允许悬空 | 目标世界脚下没地是**合法且高频使用**的谜题手段（"踩空救命"） |
| S7 | 切换后不可能卡墙 | 由判定规则保证：切换成功的前提就是目标位置全空 |

> **S7 是一个可以证明的性质**，不需要额外的"脱困"逻辑。请勿为了"保险"再加一套挤人逻辑，那只会引入穿墙 bug（见 §13 R3）。

### 2.3 由机制推导出的关键设计模式

下面三种模式是本作全部谜题的素材库。8 个关卡全部从这里出发。

**模式 A — 踩空救命（静态）**
玩家在光世界跑到坑边起跳，在空中切到暗世界，暗世界同位置是实心地面，玩家安全落地。
*教学价值*：教会玩家"切换可以凭空造出地板"。

**模式 B — 天花板差异（动能）**
光世界在某段路的上方有低矮天花板，玩家的上升被截断，跳跃高度被压缩到 1 格；暗世界同一位置没有天花板，可以跳出完整的 2.33 格。
*教学价值*：教会玩家"切换可以释放被压抑的高度"。这是最能体现"切换的瞬间才是本体"的模式，因为**静止时切换完全无效，必须在上升过程中切换**。

**模式 C — 危险错位（代价）**
光世界的熔岩区，在暗世界是安全地面；而暗世界别处也有熔岩，光世界那处却是安全的。
*教学价值*：教会玩家"每边都有代价"，制造必须计算切换时机的取舍。

## 3. 世界关系的设计范围

### 3.1 本版本采用（仅此两种）

**① 实体互补** — 同一坐标，一个世界是空的，另一个世界是实心瓦片。
覆盖：地板有无、天花板有无、墙壁有无。派生出的三种用法即 §2.3 的模式 A 与模式 B。

**② 危险互补** — 同一坐标，一个世界是致命的，另一个世界是安全的。
覆盖：熔岩/尖刺的有无与位置错位。派生出的用法即 §2.3 的模式 C。

### 3.2 本版本明确不做

| 关系类型 | 为什么不做 |
| --- | --- |
| 物理常数互补（两个世界重力不同 / 速度不同） | **最可惜的一条**。它能让两个世界的"手感"不同，是扩大谜题空间最省力的手段。但用户决定本版本不做；若 8 关做完后仍有余力，这是第一个应该加回来的扩展（见 §14） |
| 物体状态互补（可推箱子的位置在两个世界不同） | 需要额外实现可推物体、物体在世界切换时的归属规则，工作量超出三天预算 |
| 通行权互补（A 的门由 B 的开关控制） | 需要开关/门的因果链系统；关卡几何本身已能保证"单世界无解"，暂不需要 |
| 时序互补（消失砖块的跨世界同步） | 引入时间维度会让关卡调试难度陡增 |
| 颜色/相位系统 | 与光暗主题视觉上冲突，且本质是第三种状态维度，会稀释核心机制 |

### 3.3 只有两种关系时，靠什么让 8 关不雷同

这是本设计方案最大的风险（§13 R2）。**必须**用下面这张清单，按顺序逐级加大难度。每关至少推进两个维度。

| 递进维度 | 从 → 到 | 用在哪一关 |
| --- | --- | --- |
| **切换点的宽度** | 4 格宽的安全区 → 1 格宽的窗口 | L1 → L4 |
| **高度差** | 平地切换 → 需要精确落在 2 格台地边缘 | L1 → L5 |
| **切换时机** | 静止时切也行 → **必须在上升段切，下落段切必死** | L2 → L5 |
| **切换次数** | 1 次 → 4 次 | L1 → L8 |
| **危险密度** | 无危险 → 熔岩紧贴最优路线 | L1 → L6 |
| **回路** | 终点在右侧、一路向右 → 必须往回走再绕回 | L6 |

> **注意**：因为只有"实体互补 + 危险互补"两种静态关系，所有谜题本质上都是"**找对切换点**"。因此上面 6 个维度中，**"切换时机"和"高度差"是唯一能制造动态难度的两个**，务必在 L5 和 L7 用足。

## 4. 玩家操作与运动手感

### 4.1 按键表

| 操作 | 主键 | 备用键 | 说明 |
| --- | --- | --- | --- |
| 左移 | `A` / `←` | — | |
| 右移 | `D` / `→` | — | |
| 跳跃 | `Space` / `W` / `↑` | — | 可变高度，按住跳得高 |
| **切换世界** | `J` | `Shift` | 核心操作，必须放在右手能高频点击的位置 |
| 重开本关 | `R` | — | 无限撤销，随时可用，无延迟 |
| 暂停 | `Esc` | `P` | |

> **设计约束**：玩家手上只有 **4 个功能键**（左、右、跳、切）。这是刻意的——键越少，"切世界"就越像呼吸。**不要**再为重力翻转单独设一个键；重力差异如果要加，那是"两个世界的属性差异"，不是玩家的技能（见 §3.2）。

### 4.2 运动参数表（**Day 1 必须冻结**）

| 参数 | 初始值 | 单位 | 说明 |
| --- | --- | --- | --- |
| 瓦片尺寸 | 32 | px | 像素画标准尺寸；物理量以「格」为单位，改像素尺寸不影响任何物理参数 |
| 逻辑画布 | 640 × 384 | px | 20 × 12 格，宽高比正好 5:3（见 §7.5.1） |
| 重力加速度 `g` | 42 | 格/s² | |
| 跳跃初速度 `v₀` | 14 | 格/s | |
| **最大跳跃高度** | **≈ 2.33** | 格 | `v₀² / (2g)` |
| **滞空时间** | **≈ 0.67** | s | `2·v₀ / g` |
| 水平最大速度 | 5.5 | 格/s | |
| **全力跳跃水平距离** | **≈ 3.68** | 格 | 最大速度 × 滞空时间 |
| 地面加速度 | 60 | 格/s² | 约 0.09 s 到全速 |
| 空中加速度 | 35 | 格/s² | 空中控制略弱于地面 |
| 最大下落速度 | 22 | 格/s | 防止穿透 |
| 松手上升减速倍率 | ×2.2 | — | 可变跳跃高度 |
| 土狼时间（Coyote Time） | 0.10 | s | 离开地面后仍可起跳 |
| 跳跃输入缓冲 | 0.10 | s | 落地前按跳会缓存并生效 |
| 固定物理步长 | 1/120 | s | 见 §4.4 |

#### 由参数推导出的**硬性关卡设计约束**

以下三条是上面数值的数学结果，关卡设计时必须遵守（§6 的关卡数据由脚本校验）：

1. **所有"跳不过去"的坑，宽度必须 ≥ 5 格**（水平跳跃距离 3.68 格）。
2. **所有"跳不过去"的墙，高度必须 ≥ 4 格**（最大跳跃高度 2.33 格）。
3. **所有"需要跳上去"的台地，高度必须 ≤ 2 格。**

> 数值检查：跳跃高度 2.33 格 < 4 格墙高 ✓；水平距离 3.68 格 < 5 格坑宽 ✓。§6.4 的 L1 实例符合全部三条。

### 4.3 手感保障（不可省略）

这三项是"手感怪怪的"的常见根因，必须实现：

- **土狼时间 0.10 s**：玩家刚离开平台边缘的 100 ms 内仍然可以起跳。
- **跳跃输入缓冲 0.10 s**：玩家在落地前 100 ms 按下的跳跃会被缓存，落地瞬间自动触发。
- **可变跳跃高度**：松开跳跃键时，若 `vy` 仍在上升，则将 `vy` 乘以 0.45（或施加上升减速），实现"轻点小跳、长按大跳"。

### 4.4 帧率无关（硬性技术要求）

物理必须以**固定步长 1/120 s** 推进，用累加器模式：

```js
const FIXED_DT = 1 / 120;
let acc = 0;
function frame(now) {
  acc += Math.min(elapsed, 0.25);      // 防止切标签页后爆炸
  while (acc >= FIXED_DT) {
    update(FIXED_DT);
    acc -= FIXED_DT;
  }
  render();
}
```

**理由**：解谜关卡依赖精确的抛物线轨迹。如果物理直接使用可变 `dt`，那么 60 Hz 显示器与 144 Hz 显示器上的跳跃高度会有可观测差异，玩家会看到"别人的攻略在我这里过不去"，这对解谜游戏是致命的。

### 4.5 键位自定义

§4.1 的按键表是**默认绑定**，全部 6 个动作均可由玩家重绑。

#### 4.5.1 可重绑动作与槽位

| 动作 id | 默认绑定 | 槽位数 | 是否可重绑 |
| --- | --- | --- | --- |
| `moveLeft` | `KeyA`、`ArrowLeft` | 2 | ✓ |
| `moveRight` | `KeyD`、`ArrowRight` | 2 | ✓ |
| `jump` | `Space`、`KeyW`、`ArrowUp` | 3 | ✓ |
| `switchWorld` | `KeyJ`、`ShiftLeft` | 2 | ✓ |
| `restart` | `KeyR` | 1 | ✓ |
| `pause` | `Escape`、`KeyP` | 2 | ✓ |
| 取消重绑 | `Escape` | 1 | ✗ 固定不可改 |

> **每个动作支持多个槽位是必要的**：否则玩家把跳跃改到别的键之后，就再也不能用空格跳了，会觉得"改键把我的键改没了"。多槽位让改键始终是"增加一个键"，而不是"替换掉一个键"。

#### 4.5.2 **必须使用 `event.code`，绝不能用 `event.key`**（硬性技术要求）

| | `event.code` | `event.key` |
| --- | --- | --- |
| 按下物理 A 键 | `"KeyA"` | 英文布局下是 `"a"`；**中文输入法下可能是 `"Process"`、全角字符，或根本不触发** |
| 作用 | 表示**物理键位**，与输入法、键盘布局无关 | 表示**输入的字符**，只适合做文字输入 |

- **绑定时存 `event.code`，运行时比较 `event.code`。**
- 若使用 `event.key`：中文输入法环境下玩家按 `W` 可能什么都触发不了，跳跃直接失灵。**答辩现场如果老师的电脑开着中文输入法，游戏会当场罢工。** 这不是小概率事件，是必测项（§12.5 E8）。

#### 4.5.3 重绑交互流程

```
暂停菜单 → 「按键设置」→ 列出 6 个动作的当前绑定
  → 点击某个槽位 → 进入「等待输入」状态（该行显示"请按键…"）
  → 捕获下一个 keydown：
      是 Escape        → 取消本次重绑，恢复原值
      是禁止绑定的键    → 拒绝并提示（见 §4.5.4）
      已被其他槽位占用  → 拒绝，高亮冲突项并提示"该键已用于 跳跃"
      否则             → 写入该槽位，播放切换成功音效，退出等待状态
  → 「恢复默认」按钮：一键还原全部绑定，需二次确认
```

#### 4.5.4 禁止绑定的键

| 禁止 | 理由 |
| --- | --- |
| `F5`、`F11`、`F12`、`MetaLeft`／`MetaRight` | 浏览器或系统抢先处理，绑了也抢不到 |
| `Escape` | 系统固定用于「取消重绑」与「暂停」 |
| 与 `Ctrl` / `Alt` 组合的键 | 容易触发浏览器快捷键（`Ctrl+W` 会直接关掉标签页） |
| `Tab` | 会移走键盘焦点 |
| 已被其他槽位占用的键 | 一个键只能对应一个动作，避免歧义 |

#### 4.5.5 持久化与文案联动

- 存储：与成绩**分开**存 `dual-world.settings`，结构 `{ version: 1, bindings: { jump: ["Space","KeyW","ArrowUp"], ... } }`。
- **容错规则同 §8.4**：解析失败、字段类型不对、出现未知动作 id 时，**逐字段回退到默认值**，绝不因为设置损坏而打不开游戏。
- **所有面向玩家的按键提示必须动态生成，不得硬编码**：
  - §6.3 关卡提示（如"按 `J` 切换世界"）必须读取 `switchWorld` 的当前主绑定。
  - 标题画面、暂停菜单、结算界面的操作提示同理。
  - 实现上提供唯一一个 `keyLabel(actionId)` 函数，把 `code` 转成显示文本（`KeyA` → `A`，`Space` → `空格`，`ArrowLeft` → `←`），全项目只此一处做这个转换。

> **这一条极易被忽略**：如果 L1 的提示写死"按 J"，玩家把切换键改成 `K` 之后，提示就在骗他。而这恰好是 §12.2 B4 那条"不说话试玩"验收项最容易暴露的失败。

## 5. 游戏元素定义

### 5.1 瓦片类型表（ASCII 字符定义）

| 字符 | 名称 | 实心 | 致命 | 世界归属 | 说明 |
| --- | --- | --- | --- | --- | --- |
| `#` | 实心砖 | ✓ | — | 各自独立 | 光世界的 `#` 与暗世界的 `#` 是两个独立实体 |
| `.` | 空气 | — | — | — | 可通行 |
| `X` | 熔岩 / 尖刺 | — | ✓ | 各自独立 | 玩家碰撞盒与之重叠即死亡 |
| `P` | 起点 | — | — | **共用** | 两个网格各写一份，坐标必须一致，见 §5.2 |
| `E` | 终点 | — | — | **共用** | 两个网格各写一份，坐标必须一致，见 §5.2 |
| `=` | 单向平台 | 仅上方 | — | 各自独立 | **可选功能**，Day 3 有余力才做；不做则从关卡中移除 |

### 5.2 起点与终点的共用规则

- `P` 与 `E` 在**两个网格中都书写**（便于单独审阅任一世界的几何时，一眼看到起终点在哪）。
- 加载时强制校验：两个网格中 `P` 的坐标必须完全相同，`E` 的坐标也必须完全相同。任一不一致即视为关卡数据错误，在控制台报出关卡 id 与两处坐标，并拒绝加载该关。
- 玩家的出生坐标取 `P` 所在的瓦片，站立姿势为"脚底贴住该瓦片的下边缘"。

> **为什么不干脆只写一份？** 因为当起终点只存在于一个网格时，审阅另一个世界的几何会失去参照物。而"写两份 + 加载期强制校验一致"既保留了可读性，又把不一致变成**硬报错**，不会静默漂移。

### 5.3 死亡与重生

| 触发条件 | 处理 |
| --- | --- |
| 玩家 AABB 与任意 `X` 瓦片重叠 | 死亡 |
| 玩家 Y 坐标超出画布下边界 | 死亡 |
| （切换失败） | **不是死亡**，只是切换被拒绝，见 §2.2 |

重生流程：

```
死亡 → 播放爆散粒子（0.25 s）→ 玩家回到起点 → 速度归零 → 可操作
```

- **总耗时必须 ≤ 0.4 s**，且期间不接受输入，但也不显示任何"Game Over"字样。
- **不扣命、不计数、不弹窗。** 玩家按 `R` 也触发同一套流程。
- 重生时 `worldIndex` **重置为光世界（0）**。这条必须写进新手引导，否则玩家会困惑。

| 关卡 | 名称 | 引入的新概念 | 使用关系 | 切换次数 | 通关预期 |
| --- | --- | --- | --- | --- | --- |
| L1 | 切换 | 切换世界本身；"凭空造出地板" | 实体互补（模式 A） | 1 | 20 s |
| L2 | 立足 | 危险错位；同一格一边安全一边致死 | 危险互补（模式 C） | 2 | 30 s |
| L3 | 连跳 | 一段路需要连续切两次 | 实体 + 危险 | 3 | 40 s |
| L4 | 窄门 | 切换点从 4 格宽收紧到 1 格宽 | 实体互补 | 3 | 50 s |
| L5 | 上升 | **必须在跳跃的上升段切换**，下落段切必死 | 实体互补（模式 B） | 2 | 60 s |
| L6 | 回头 | 终点就在右边，但必须先往回走到某处切换 | 实体 + 危险 | 3 | 70 s |

> **`hint` 字段不得硬编码按键名。** §6.1 的 `hint: '按 J 切换世界'` 只是方便阅读的示意，实际实现必须写成 `hint: (k) => \`按 ${k('switchWorld')} 切换世界\``，由 §4.5.5 的 `keyLabel()` 提供当前绑定。否则玩家改键之后，提示就在骗他（验收项 E4 专测这一条）。

### 6.5 关卡设计工作流

因为关卡会改几十遍，必须做到"改一行字符串、刷新就看到结果"：

1. 所有关卡集中在 `src/levels.js`，不在其他任何文件里出现关卡坐标。
2. 右键菜单或 URL 参数提供**直接跳关**（如 `index.html?lvl=5`），避免每次从头玩。
3. 开发模式下按 `,` / `.` 切换上一关 / 下一关。
4. 保留一个"单世界调试开关"（如按 `0` 强制进入暗世界），用来人工核验"单世界无解"。

## 7. 视觉规格

### 7.1 双世界调色板（像素画调色板）

两个世界**共用同一套几何、同一套精灵造型**，只替换调色板。这既是最省的出图方式，也制造了极强的切换反馈。

| 元素 | 光世界 | 暗世界 |
| --- | --- | --- |
| 背景 | `#F4EFE2` 暖米白 | `#14161F` 深靛 |
| 实心砖 | `#2B2B33` 近黑 | `#8A93B5` 冷灰蓝 |
| 玩家 | `#E4572E` 橙红 | `#4ECDC4` 青绿 |
| 熔岩 / 尖刺 | `#C1292E` 深红 | `#FF6B35` 亮橙 |
| 终点 | `#3D9970` 橄榄绿 | `#F5D547` 亮黄 |

- 玩家与危险物在两个世界**换色**是刻意的：让玩家在混乱的高速切换中有额外的视觉锚点。
- 这 10 个颜色构成**像素画的总调色板**（每世界 5 色）。所有瓦片、精灵、特效的配色都必须收在这个范围内——这是让 ComfyUI 产出、手绘、程序化占位图三者风格统一的关键约束（后处理见 §7.7.3）。
- 所有颜色必须是配置常量（`src/palette.js`），**不得散落在渲染代码中**；DOM HUD 通过 CSS 变量读取同一组值（见 §8.3）。
- 两套精灵可以是同一张图的两个换色版本，**不需要重新设计造型**（见 §7.5.3）。

### 7.2 叠影渲染（关键决策）

**决策：采用"叠影"，不采用双屏，也不采用纯单屏。**

| 方案 | 问题 |
| --- | --- |
| 双屏并排 | 视野被压缩一半，且削弱了切换的冲击感 |
| 纯单屏切换 | 玩家必须靠记忆记住另一个世界的形状 → 在解谜游戏里"靠记忆"等于劝退 |
| **叠影（选定）** | 显示当前世界，同时把另一个世界的实体以低透明度幽灵绘制 |

叠影的具体规格：

| 层级 | 绘制内容 | 参数 |
| --- | --- | --- |
| 1 | 当前世界背景色 | 不透明 |
| 2 | **另一世界的实体幽灵** | `globalAlpha = 0.18`，统一灰色 `#7A7A7A`，**不描边** |
| 3 | **另一世界的危险幽灵** | `globalAlpha = 0.12`，统一灰色，**不得使用危险物的颜色** |
| 4 | 当前世界的实心砖 | 不透明，带 1 px 描边 |
| 5 | 当前世界的危险物 | 不透明 + 缓慢脉动（alpha 在 0.85–1.0 之间，周期 1.2 s） |
| 6 | 玩家 | 最上层，带 2 px 白色描边以在任何背景上保持可见 |

> 危险幽灵**故意不用红色/橙色**：若幽灵也是红的，玩家会误判"另一世界的熔岩在当前世界也能杀我"。统一灰色且更低透明度，表达的是"那里有东西，但它现在不存在"。

### 7.3 切换反馈（这是全游戏最重要的反馈）

| 事件 | 视觉 | 时长 |
| --- | --- | --- |
| **切换成功** | 整屏调色板瞬间切换（不做淡入淡出）；叠加一次轻微的径向缩放 1.00 → 1.03 → 1.00；4 个方向各飞出 6 个短寿命粒子 | ≤ 0.10 s |
| **切换失败** | 屏幕边缘闪红 `#FF3B30 @ alpha 0.35`（中心透明，做成 vignette 效果）；屏幕震动幅度 4 px；玩家精灵闪白 2 帧 | 0.12 s 闪红 / 0.15 s 震动 |

- **成功反馈必须干脆**。玩家在 L7 会一秒切 5 次，任何超过 0.15 s 的过渡动画都会变成拖累。
- **失败反馈必须清晰但不惩罚**。目标是在 200 ms 内让玩家建立"这里切不过去"的直觉，而不是让他觉得被罚了。

### 7.4 其他特效

| 特效 | 规格 |
| --- | --- |
| 死亡爆散 | 16 个粒子，玩家色，初速 3–6 格/s，0.35 s 内衰减完毕 |
| 落地烟尘 | 落地时若下落速度 > 12 格/s，左右各生成 3 个粒子 |
| 通关 | 终点放大 + 8 个粒子外扩；0.6 s 后进入下一关 |
| 屏幕震动 | 用单独的 `shakeOffset` 施加在 `ctx.translate` 上，**不修改**任何游戏坐标 |
| 渲染缩放 | 画布通过 CSS 等比缩放至容器，保持 **5:3** 宽高比，加 `image-rendering: pixelated`（分级策略见 §7.5.5） |

### 7.5 美术资源规格

> **先澄清一件事**：§6 里的 ASCII 网格是**关卡几何的数据格式**（Celeste、Terraria、VVVVVV 都这么存关卡），它只存在于 `src/levels.js` 里，玩家一个字符也看不到。运行时每个 `#` 渲染成一张瓦片贴图，`X` 渲染成带动画的熔岩，玩家渲染成角色精灵。**ASCII 是给关卡设计师写关卡用的，不是给玩家看的画面。**

#### 7.5.1 分辨率链

| 层 | 尺寸 | 说明 |
| --- | --- | --- |
| 逻辑瓦片 | **32 × 32 px** | 像素画标准瓦片尺寸；也便于把 ComfyUI 的大图整数下采样到 32 / 64 |
| 逻辑游戏区 | **640 × 384 px** | 20 × 12 格，宽高比正好 **5 : 3** |
| 玩家碰撞盒 | **24 × 56 px** | 0.75 格宽 × 1.75 格高 |
| 玩家精灵画布 | **32 × 64 px** | 底部对齐碰撞盒底边，上方与两侧留出动画溢出空间（如起跳拉伸、披风飘动） |
| 显示层 | CSS 等比缩放 | 见 §7.5.5 |

> **为什么物理量用「格」而不用像素**：这样美术分辨率与物理参数完全解耦。以后想把瓦片从 32 px 换成 48 px，只需要重新出图，`g`、`v₀`、跳高跳距一个都不用动，8 个关卡也不用重做。**这是 §6.4 的 L1 在改了瓦片尺寸后依然有效的原因**——本次把瓦片从 40 px 改成 32 px，物理与关卡数据零改动。

#### 7.5.5 缩放策略（分级，按可用空间降级）

```
可用空间 = 容器宽高（减去 HUD 高度）
整数倍 = floor(min(可用宽 / 640, 可用高 / 384))
  整数倍 >= 2  → 用整数倍缩放（最清晰，像素严格等大）
  整数倍 == 1  → 用整数倍 1（画布偏小，但像素完美）
  整数倍 == 0  → 退化为非整数等比缩放（会略微不均，但保证铺满）
```

| 屏幕 | 可用高度（减去 40 px HUD） | 结果 |
| --- | --- | --- |
| 1920 × 1080 | 1040 | 2 倍（1280 × 768），四周留边 ✓ |
| 2560 × 1440 | 1400 | 3 倍（1920 × 1152）✓ |
| 1366 × 768 | 728 | 1 倍偏小 → **退化为 1.89 倍**（1290 × 728） |

> 非整数缩放会让部分像素比相邻像素宽 1 px，仔细看能看出不均。这是**可接受的取舍**：为它专门去缩短网格高度会牺牲关卡设计空间。如果后期确实在意，唯一的正解是把网格从 12 行减到 10 行（640×320，2 倍正好塞进 768），但那要重做全部关卡，**本版本不做**。

### 7.6 素材来源、热替换与降级

素材有三个来源，**优先级从低到高**，同名覆盖：

| 优先级 | 来源 | 何时用 | 产物 |
| --- | --- | --- | --- |
| 1（兜底） | **程序化生成**（`src/procedural.js`） | 永远可用 | 代码绘制，无文件 |
| 2 | **手绘或脚本生成的 PNG** | Day 1 起 | `assets/` 下的 PNG |
| 3 | **ComfyUI 产出**（见 §7.7） | Day 3 或上线后 | 覆盖同名 PNG |

#### 7.6.1 加载与降级规则（**必须实现**）

```
启动 → 读取 assets/manifest.json
     → 逐项加载对应 PNG
        成功且尺寸符合声明  → 建纹理，按 manifest 切帧
        失败 / 尺寸不符 / 解析异常 → 回退到 procedural.js 的同名占位绘制
                                   → 控制台 warn（不弹窗、不阻塞）
     → 全部处理完毕后进入标题画面
```

> **为什么必须做降级**：三天项目里最容易出现的致命场景是"素材还没画完，游戏就白屏了"。有了降级，**任何时刻游戏都是可玩、有画面的**；素材只是逐步替换上去的贴图。这也是本作能在答辩现场稳定演示的保险。

#### 7.6.2 `manifest.json` 结构

```json
{
  "version": 1,
  "tileSize": 32,
  "sheets": {
    "player.light": { "src": "player/player-light.png", "frameW": 32, "frameH": 64,
                      "anims": { "idle": [0,1,2,3], "run": [4,5,6,7,8,9], "jump": [10,11],
                                 "fall": [12,13], "land": [14,15], "die": [16,17,18,19] } },
    "tiles.light":  { "src": "tiles/tileset-light.png", "frameW": 32, "frameH": 32 },
    "hazard.light": { "src": "hazard/lava-light.png", "frameW": 32, "frameH": 32, "fps": 8 },
    "exit.light":   { "src": "ui/exit-light.png", "frameW": 32, "frameH": 32, "fps": 6 }
  }
}
```

- **所有帧偏移、动画帧序、播放速率一律从 manifest 读取，渲染代码里不得出现硬编码的像素数字。** 这样新出的图只要文件名与尺寸符合约定，丢进 `assets/` 就自动生效，零代码改动。
- `frameW` / `frameH` 与 `tileSize` 或实际图片尺寸不符时，按加载失败处理，走 §7.6.1 的降级。

### 7.7 ComfyUI 接入（**离线出图工具，不是运行时依赖**）

#### 7.7.1 绝对不能在游戏运行时调用 ComfyUI

| 原因 | 说明 |
| --- | --- |
| 混合内容拦截 | Pages 是 `https://`，ComfyUI 本地服务是 `http://127.0.0.1:8188`。浏览器会把这类请求当作混合内容**直接拦截**，代码再对也没用 |
| 用户环境不存在 | 老师、同学的电脑上并没有跑 ComfyUI |
| 托管代价 | 把 ComfyUI 暴露到公网既昂贵又不安全，且违背 §1.4「完全没有后端」的边界 |

**正确用法**：ComfyUI 是你**本地离线出图**的工具。产出的 PNG 经后处理（§7.7.3）后手动放进 `assets/`，随 git 提交上线。**游戏运行时对 ComfyUI 零依赖。**

#### 7.7.2 ComfyUI 能做什么、不能做什么

| | 适合交给 ComfyUI | 必须程序生成或手绘 |
| --- | --- | --- |
| **推荐** | 标题 key art、结局插画、视差远景背景（`bg-light/dark.png`）、UI 装饰边框、README 与答辩用的 capsule 图 | — |
| **不推荐** | — | **瓦片集**：SD 类模型无法保证左右／上下边缘无缝拼接，也无法保证 32×32 网格严格对齐 |
| | | **角色精灵表**：无法保证帧与帧之间造型、比例、脚点一致，做出来的动画会抽搐 |
| **折中** | 若一定要用 ComfyUI 出角色：**只出单帧立绘**，用在标题画面与结算画面（静态），不要做动画帧 | 动画帧仍然程序生成 |

> **一句话分工：背景与插画交给 ComfyUI，瓦片与角色交给程序生成或手绘。** 想让 SD 直接吐出一张能用的 32×32 无缝瓦片集，通常比手画还慢——这属于"看起来很美好、实际会吃掉一整天"的坑。

#### 7.7.3 若确实要用 ComfyUI 出瓦片，后处理链必须补齐

```
ComfyUI 出图（1024×1024 或更大）
  → 裁切出单个瓦片（人工对齐到网格）
  → 最近邻下采样到 32×32        ← 绝不能用双线性／双三次，会糊成一团
  → 调色板量化到 §7.1 的 5 色以内
  → 无缝检查（左右／上下拼接后放大看有没有缝）  ← 必须做
  → 去背 / 补 alpha 通道
  → 存入 assets/tiles/tileset-<world>.png
```

- 第 4 步（无缝检查）不能省：有缝的瓦片铺成一整面墙后，会露出规则的网格线，非常显眼。
- 建议用 Python + Pillow 把这套流程固化成 `tools/prep-assets.py`，避免每次手动重复。

## 8. 计时与成绩系统

### 8.1 定位与边界（**先读这一条**）

计时在本作中是**纯记录层，不影响任何玩法**。

| 允许 | 禁止 |
| --- | --- |
| 记录并显示本关用时、累计总用时 | 倒计时 |
| 记录本关与全流程的切换次数 | 限时机关 / 时间奖励 |
| 记录并持久化个人最佳成绩 | 排行榜 / 联网对比 / 好友数据 |
| 在结算界面展示成绩 | 任何"时间不够就失败"的机制 |

> **为什么必须把这条边界写死**：本作是解谜游戏，§1.2 法则 3 要求"失败零代价、让玩家敢想"。一旦时间变成胜负条件，玩家就会为了成绩而回避试错，游戏立刻退化成手残跑酷——这正是法则 3 要防的事。计时可以存在，但只能作为**事后回顾**的数据。

### 8.2 计时规则

**核心实现决策：计时器累加固定物理步长，绝不使用墙钟时间（`Date.now()` 或 `performance.now()` 差值）。**

```js
// 在 §10.4 主循环的每个固定步内执行，仅当状态为 PLAYING 时累计
if (state === 'PLAYING') {
  levelTimeMs += FIXED_DT * 1000;
  totalTimeMs += FIXED_DT * 1000;
}
```

这一个 `if` 同时免费获得三个正确性质，不需要额外写任何代码：

| 性质 | 为什么自动成立 |
| --- | --- |
| 暂停时不涨 | `PAUSED` 状态不进入累加分支 |
| 切标签页 / 最小化回来不暴涨 | 累加器已把单帧 `elapsed` 钳制在 0.25 s 内（§10.4），切回来最多补 0.25 s |
| 帧率无关 | 与 §4.4 同源；120 Hz 与 60 Hz 下累计值完全一致 |

> **反面教材**：若改用 `performance.now()` 的差值计时，玩家切走 5 分钟再回来会凭空多出 5 分钟成绩。这是本系统唯一一个"看起来能用、其实是错的"实现方式。

| 规则 | 定义 |
| --- | --- |
| 计时对象 | ① **本关用时** ② **累计总用时**（从第 1 关首次获得操作权起，跨关连续累计） |
| 本关计时开始 | 关卡加载完成、玩家首次获得操作权的瞬间（`state` 进入 `PLAYING`） |
| 本关计时停止 | 玩家碰到终点的瞬间 |
| 累计计时停止 | 第 8 关通关的瞬间 |
| **死亡是否重置本关计时** | **不重置。** 死亡与按 `R` 重开都只是回到起点，时间继续累计 |
| 暂停是否停止计时 | **停止** |
| 结算画面是否计时 | **不计时**（`LEVEL_CLEAR` 不属于 `PLAYING`） |
| 精度 | 内部毫秒；显示 `mm:ss.cc`（分:秒.厘秒），超过 1 小时显示 `h:mm:ss.cc` |
| 切换次数计数 | 只在切换键**按下沿**且**切换成功**时 +1；失败的切换不计入（§10.5） |

> **"死亡不重置计时"是刻意的，且与 §5.3 完全一致。** 若死亡就清零计时，玩家会为了成绩而不敢试错——那等于把失败重新变成有代价，直接违反法则 3。因此成绩天然包含所有失败时间，这是可接受的：本作比的是"想清楚"，不是"手速"。

### 8.3 HUD 布局

**决策（v0.3 变更）：HUD 用 HTML/CSS 的 DOM 元素实现，不画进 canvas。canvas 只负责 20×12 的游戏区。**

```
┌──────────────────────────────────────────────────────────┐
│  第 5 关 / 8   本关 00:12.34   总计 02:41.07   切换 7 次   │  ← HUD：DOM 元素，高 40 px
├──────────────────────────────────────────────────────────┤
│                                                          │
│              <canvas> 640 × 384（20 × 12 格）             │
│                                                          │
└──────────────────────────────────────────────────────────┘
```

| 项 | 规格 |
| --- | --- |
| HUD 实现方式 | 普通 HTML `<div>` + CSS，**不在 canvas 内绘制** |
| 逻辑画布尺寸 | **640 × 384**，宽高比 **5 : 3**，只包含游戏区（§7.5.1） |
| HUD 高度 | 40 px；可用 `clamp(32px, 5vh, 48px)` 做自适应 |
| HUD 字体 | 系统字体即可，**不需要像素字体**——DOM 文本在任何 DPI 下都清晰 |
| 数字不抖动 | 数字部分加 `font-variant-numeric: tabular-nums`，一行 CSS 解决 |
| 主题联动 | 切换世界时给容器加／删 class（`world-light` / `world-dark`），颜色由 CSS 变量驱动（§7.1） |
| 响应式 | 外层 `display:flex; flex-direction:column; align-items:center`；canvas 用 `max-width` / `max-height` 等比约束（§7.5.5） |
| 遮挡 | HUD 与 canvas 是兄弟节点，**物理上不可能重叠** |

> **为什么 v0.2 的"canvas 内 HUD + 800×520"被推翻**：① 在 canvas 里画文字要额外做像素字体，缩放后还会糊；② 把 HUD 塞进 canvas 会让需要等比缩放的面积从 640×384 涨到 640×424，在 1366×768 这类笔记本上会逼出更难看的非整数缩放；③ DOM 方案下"数字跳变不抖动"用一行 `tabular-nums` 就解决了。**DOM HUD 更简单、更清晰、更省事。**

### 8.4 成绩持久化

`localStorage` 使用**单键**存储，避免多键写入不同步：

```js
// key: 'dual-world.records'
{
  version: 1,
  levelBestMs:  { "1": 18340, "2": 29810 },     // 每关最佳用时
  levelBestSw:  { "1": 1, "2": 2 },             // 每关最少切换次数
  runBest: { timeMs: 512300, switches: 41, date: "2026-10-07" }  // 全流程最佳
}
```

| 项 | 规格 |
| --- | --- |
| 写入时机 | **仅在**关卡通关 / 全流程通关时写入；页面加载时读取一次并缓存到内存 |
| 破纪录反馈 | 结算界面显示 `NEW RECORD` 并播放 §9 的通关琶音；未破纪录则显示与最佳的差值（如 `+ 00:03.21`） |
| 清空记录 | 暂停菜单内提供"清空成绩"按钮，需二次确认 |
| **容错（必须做）** | 读取时 `try/catch` 并校验 `version` 与字段类型；解析失败就丢弃并重建，**绝不能让损坏的存档导致游戏打不开** |
| 隐私模式 | Safari 无痕等环境下 `localStorage` 可能直接抛异常，必须捕获并降级为"仅本次会话内有效"，且不弹任何报错 |

### 8.5 通关结算界面

| 显示项 | 本关结算 | 全流程结算 |
| --- | --- | --- |
| 本关用时 | ✓（大字） | — |
| 本关最佳 + 差值 | ✓ | — |
| 累计总用时 | ✓ | ✓（大字） |
| 本关切换次数 | ✓ | — |
| 累计切换次数 | — | ✓ |
| 最少切换次数纪录 | — | ✓ |
| 操作提示 | "按 `Space` 进入下一关" | "按 `R` 重新开始挑战" |

- 结算界面**不显示任何评级 / 星级 / SABC 等级**。理由同 §8.1：本作不把时间变成评价。
- 结算界面本身**不计时**（§8.2）。

## 9. 音频规格

**全程使用 Web Audio API 程序合成，不引入任何音频文件。**（零素材依赖，同时避免 Pages 上的路径与版权问题）

| 事件 | 合成方式 | 听感 |
| --- | --- | --- |
| 跳跃 | 正弦波，频率 520 → 780 Hz | 短促上扬 |
| 落地 | 三角波，220 Hz，0.06 s 衰减 | 闷响 |
| **切换成功** | 方波，频率 880 Hz，0.05 s | 清脆 "blip" |
| **切换失败** | 锯齿波，160 Hz，0.12 s，带轻微降调 | 低沉的 "buzz" |
| 死亡 | 白噪声 + 低通滤波扫频 | 散开感 |
| 通关 | 三音上行琶音（523 / 659 / 784 Hz） | 明亮 |

**技术要求**：

- `AudioContext` 必须**在首次用户手势时创建或恢复**（浏览器自动播放策略）。
- 因此标题画面的"按任意键开始"承担双重职责：解锁音频 + 开始游戏。**不要**在页面加载时就创建 `AudioContext`。
- 必须先判断 `AudioContext.state`，在 `suspended` 时调用 `resume()`。
- 总音量控制在 0.15 以内，避免答辩现场音响炸裂。

## 10. 技术方案

### 10.1 技术栈

| 项 | 选择 | 理由 |
| --- | --- | --- |
| 渲染 | 原生 `<canvas>` 2D | 无依赖，性能足够，AI 改写最不容易乱 |
| 语言 | 原生 JavaScript（ES Modules） | 不需要构建步骤，Pages 直接可用 |
| 构建工具 | **无** | 少一个环节就少一类翻车方式 |
| 第三方库 | **无** | 零依赖 = 零版本问题 |
| 物理引擎 | 自己写 AABB | 平台跳跃的碰撞逻辑必须自己控制，否则无法实现精确手感 |

### 10.3 全局状态机

```
BOOT ──► TITLE ──► PLAYING ⇄ PAUSED
                     │  │
                     │  └──► DEAD ──► PLAYING（重生回本关起点）
                     │
                     └──► LEVEL_CLEAR ──► PLAYING（下一关）
                              │
                              └──► GAME_CLEAR（第 8 关通关）
```

- `DEAD` 与 `LEVEL_CLEAR` 都是**短暂状态**，不接受输入，自动流转。
- `PAUSED` 时必须停止物理推进，但继续渲染（画面变暗）。

### 10.4 主循环

按 §4.4 的固定步长累加器实现。每个固定步内的顺序必须严格如下：

```
1. 采样输入（含输入缓冲判定）
2. 处理世界切换请求（§2.2 判定）
3. 玩家水平移动与加速度
4. 重力积分 → 垂直移动
5. 分轴 AABB 碰撞解算（先 X 后 Y，避免斜向穿墙）
6. 危险瓦片重叠判定 → 可能进入 DEAD
7. 越界判定 → 可能进入 DEAD
8. 终点判定 → 可能进入 LEVEL_CLEAR
9. 计时累加（§8.2，仅当 state === 'PLAYING'）
```

> **第 5 步的分轴解算是必须的**：同时解算 X 与 Y 会在斜向撞击角落时产生穿透。先移动 X 并解算，再移动 Y 并解算。
>
> **第 9 步必须排在最后**：若放在第 8 步之前，通关那一帧的时间会被多算一次，成绩恒定比实际操作多约 8.3 ms（1/120 s）。顺序写错不会报任何错，只会让成绩永远差一点点。

### 10.5 输入缓冲与土狼时间的实现要点

- 跳跃键**按下沿**记入 `jumpBufferTimer = 0.10`，每帧递减。
- 玩家离开地面时记入 `coyoteTimer = 0.10`，落地时清零。
- 起跳条件：`jumpBufferTimer > 0 && coyoteTimer > 0`。
- 切换键**只在按下沿触发**，不响应长按（否则按住就会疯狂切换，观感崩坏）。

### 10.6 本地开发与部署

**本地运行**：ES Modules 无法通过 `file://` 协议工作（CORS 限制）。但不需要安装任何东西——仓库自带 `tools/dev-server.mjs`，用 Node 内置模块写一个静态服务器：

```bash
node tools/dev-server.mjs      # 然后访问 http://localhost:5173
```

**部署到 GitHub Pages**：

1. 仓库设为 **Public**。
2. `Settings → Pages → Source: Deploy from a branch → main / (root)`。
3. 等待 1–2 分钟，访问 `https://<用户名>.github.io/<仓库名>/`。

| 部署注意项 | 说明 |
| --- | --- |
| 所有资源路径必须用相对路径 | 用 `./src/main.js`，**不能**用 `/src/main.js`（会 404） |
| 两个文件名的坑 | 不要出现以 `_` 开头的文件/目录（Jekyll 会吞掉）；`.nojekyll` 可彻底规避 |

| 大小写敏感 | Pages 运行在 Linux 上，`Player.js` 与 `player.js` 是不同的文件。**所有 import 路径必须与实际文件名大小写完全一致** |
| 缓存 | 部署后若看到旧版本，用 `Ctrl + F5` 强制刷新 |

## 12. 验收标准

### 12.1 功能验收

| 编号 | 验收项 | 判据 |
| --- | --- | --- |
| A1 | 8 关全部可通关 | 逐关完整走通一次 |
| A2 | **每关"单世界无解"** | 每关提交一份书面推理（格式见 §6.4），且用 §6.5 的调试开关人工核验一次 |
| A3 | 切换保留速度 | 在跳跃上升段切换后，继续上升的高度与不切换时一致 |
| A4 | 切换失败无副作用 | 连续快速点击切换键，位置与速度不受任何影响 |
| A5 | 起点终点世界共享 | 两个世界的 `P` / `E` 坐标一致（由 V6 保证） |
| A6 | 死亡重生 ≤ 0.4 s | 秒表计时 |
| A7 | 音频延迟 | 首次按键后音效正常，无 "AudioContext was not allowed to start" 警告 |
| A8 | 无报错 | 完整通关一次，控制台零 error |

### 12.2 手感验收（主观但必须做）

| 编号 | 验收项 |
| --- | --- |
| B1 | 连续跳跃 20 次，不出现"明明按了却没跳"的挫败 |
| B2 | 在平台边缘起跳，土狼时间感觉自然（不是"莫名其妙还能跳"） |
| B3 | 切换键连按 10 次，反馈清晰且不卡顿 |
| B4 | 让一个没玩过的人试玩 L1，**不说话**观察他是否能在 60 秒内自己悟出切换 |

> **B4 是全项目最重要的一条验收项。** 如果试玩者需要你解释，说明 L1 的教学设计失败了，必须改关卡而不是改讲解。

### 12.3 工程验收

| 编号 | 验收项 | 判据 |
| --- | --- | --- |
| C1 | 帧率无关 | 在 60 Hz 与 120 Hz 环境下，从同一起点起跳的最大高度误差 < 0.05 格 |
| C2 | 稳定 60 FPS | Chrome DevTools Performance 面板 10 秒无掉帧 |
| C3 | 响应式 | 1920×1080、1366×768、手机竖屏 三种视口下无横向滚动条，画布等比居中 |
| C4 | 线上可用 | Pages 地址在手机 4G 与电脑上都能打开并通关 |
| C5 | 无绝对路径 | 全局搜索 `/src/`、`/assets/`，零结果 |
| C6 | 大小写一致 | 所有 import 路径与实际文件名逐字符一致 |

### 12.4 计时验收（D 组）

| 编号 | 验收项 | 判据 |
| --- | --- | --- |
| D1 | 暂停不计时 | 暂停 30 s 后恢复，成绩只增加实际游玩时间（误差 < 0.1 s） |
| D2 | 切标签页不暴涨 | 切走 3 分钟再回来，成绩最多增加 0.25 s（§8.2 的钳制） |
| D3 | 死亡不清零 | 故意死 5 次后通关，成绩 ≈ 全部游玩时间之和 |
| D4 | 存档容错 | 手动把 `localStorage` 里的 `dual-world.records` 改成非法字符串，刷新后游戏正常启动且成绩被重建 |
| D5 | 不遮挡 | HUD 与 canvas 是兄弟节点，视觉上不重叠；1920×1080 下 canvas 保持 5:3 |
| D6 | 数字不抖动 | 用时从 `00:09.99` 跳到 `00:10.00` 时，HUD 各字段不发生水平位移（`tabular-nums` 生效） |

### 12.5 美术与键位验收（E 组）

| 编号 | 验收项 | 判据 |
| --- | --- | --- |
| E1 | **画面不是字符** | 截图放大后，砖块与角色是贴图或程序化图形；**屏幕上不出现任何 ASCII 字符**（HUD 数字除外） |
| E2 | 素材降级可用 | 把 `assets/` 整个改名，刷新后游戏仍能启动、可玩、不白屏，控制台出现 warn |
| E3 | 热替换生效 | 只替换 `tileset-light.png` 一张图，刷新后画面更新，**零代码改动** |
| E4 | 改键立即生效 | 把切换键改成 `K`，游戏内立即用 `K` 生效，**且 L1 的提示文案同步变成"按 K 切换世界"** |
| E5 | 改键持久化 | 改键后刷新页面，绑定仍是新键 |
| E6 | 冲突拒绝 | 把跳跃绑到已被占用的 `KeyA`，界面拒绝并提示占用者 |
| E7 | 设置损坏容错 | 把 `dual-world.settings` 改成非法 JSON，刷新后游戏正常启动且绑定为默认值 |
| E8 | **中文输入法下可用** | 系统切到中文输入法，所有按键仍然正常触发（验证用的是 `event.code` 而非 `event.key`） |

> **E8 是这一组里最容易漏测、后果最严重的一条。** 它不需要写任何新代码，只需要你亲手把输入法切成中文再玩一遍。答辩现场用的是别人的电脑，这条不做就是赌运气。
